## What the docs say

From the releasing page:

- "Ensure your `gemini-extension.json` file is in the absolute root of the repository or the release archive." For GitHub Release archives: the file "must be at the root of the archive".
- The extension must be hosted in a public GitHub repository.
- Add the `gemini-cli-extension` topic to the repository's About section.
- No submission is needed: "You don't need to submit an issue or email us to list your extension." The gallery crawls tagged repositories daily, and an extension appears if it passes validation after being tagged. The page does not describe what the validation checks.
- Users install with `gemini extensions install <repo-uri>`, optionally pinned with `--ref`. With GitHub Releases the CLI checks the release marked Latest; custom archives must be self-contained and follow a naming pattern such as `{platform}.{arch}.{name}.{extension}`.

From the reference page:

- Each extension needs `gemini-extension.json` in its root directory.
- `name` should be lowercase letters or numbers with dashes, and "we expect this name to match the extension directory name".
- `mcpServers` uses the same options as `settings.json` (except `trust`); `${extensionPath}` refers to files in the extension.
- `contextFileName` names the context file; if omitted and a `GEMINI.md` exists in the extension directory, it is loaded.
- The page does not cover gallery validation.

## The root question (finding 6.8)

The real manifest is `packages/aegis/gemini-extension.json`, beside `packages/aegis/GEMINI.md`. The repository root has neither file. By the docs above, installing from the repository URI and gallery discovery both look for the manifest at the repository root, or at the root of a release archive. A manifest under `packages/aegis/` satisfies neither.

Options, for the maintainer to choose (this runbook does not pick one):

| Option | What it takes | Notes |
|---|---|---|
| A. Release archive | Phase 7 attaches an archive to the GitHub release whose root is the extension: `gemini-extension.json`, `GEMINI.md` and the skills content. Install with `gemini extensions install https://github.com/drupadsachania/aegis-skills` using the Latest release | Matches the "release archive root" wording and keeps the monorepo layout. The archive must be self-contained and follow the documented naming pattern; the docs give the pattern only as an example |
| B. Root-level files | Add `gemini-extension.json` and `GEMINI.md` at the repository root (a copy, or generated by a script from `packages/aegis`) | Simple for discovery. Adds a second copy that must be kept in sync, which is exactly what `scripts/check-layout.js` would have to start checking |
| C. Separate repository | A small public repository containing only the extension | Cleanest for the gallery; adds a repository to maintain |

Whichever is chosen, the manifest `name` is `aegis-skills`, and the docs expect the name to match the extension directory name, which the repository name `aegis-skills` satisfies for options A and B.
